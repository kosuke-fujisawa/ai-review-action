# Evidence filter 有効性評価

実施日: 2026-07-31

## 結論

現在のevidence filterは有効ではない。小規模変異パイロットでは、モデルが検出した正解3件をすべて棄却し、誤検知1件はそのまま通過させた。

この状態では、filterを現行Actionの独自価値として公開できない。

## 評価方法

同じ `gpt-5-mini` 応答に含まれる全候補をfilter適用前、`parseReviewJson` が採用した候補をfilter適用後として対比較した。

別々のモデル呼び出し同士を比較していないため、モデル出力の揺れをfilterの効果として数えていない。正解ラベルはモデルではなく、事前に定義した変異と実行結果から割り当てた。

### 変異ケース

- 認証条件を `token === expectedToken` から `!==` へ反転
- 配列末尾を `items.length - 1` から `items.length` へ変更
- キャッシュ削除先を `cacheDir` から永続データの `dataDir` へ変更

各変異の修正差分も負例として実行した。合計は正例3件、負例3件である。

## パイロット結果

| Variant | TP | FP | FN | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| filter適用前 | 3 | 1 | 0 | 0.750 | 1.000 | 0.857 |
| filter適用後 | 0 | 1 | 3 | 0.000 | 0.000 | 0.000 |

| 効果 | 結果 |
| --- | ---: |
| 誤検知削減数 | 0 |
| 誤検知削減率 | 0.0% |
| 正解削除数 | 3 |
| 正解保持率 | 0.0% |
| Precision差分 | -0.750 |
| Recall差分 | -1.000 |

## 棄却原因

正解3件はすべて、具体的な入力、実行経路、観測可能な影響、修正案を含んでいた。しかしモデルが `counterEvidence` を空文字で返したため、`meetsEvidenceGate` の「counterEvidenceは非空」という条件で `insufficient_evidence` になった。

一方、負例の誤検知は「呼び出し側が `cacheDir` を省略している場合」という差分外の仮定を置きながら、非空の `counterEvidence` を生成したためfilterを通過した。

現在のルールは、反証が見つからなかった正解より、条件付きの反証文を生成した推測を優遇している。

## 既存4ケースでの補助結果

過去PRの4ケースでは、filter適用前後は以下だった。

| Variant | TP | FP | FN |
| --- | ---: | ---: | ---: |
| filter適用前 | 0 | 5 | 3 |
| filter適用後 | 0 | 4 | 3 |

誤検知を1件（20%）削減したが、filter適用前から正解候補が0件だったため正解保持能力は評価できなかった。変異パイロットにより、正解保持に重大な問題があることが確認された。

## 判断

- 現在のfilterを公開上の差別化要素として扱わない。
- `counterEvidence` の「存在」ではなく、反証を試みた結果を構造化して扱う必要がある。
- 修正後は同じ6ケースを変更せず再実行し、少なくとも正解保持率100%を回帰条件にする。
- 公開価値を主張する前に、実プロジェクト由来の正例・負例を追加し、変異ケースだけに最適化しないことを確認する。

## 制約

- 正例3件、負例3件の小規模パイロットである。
- 変異は短く明示的で、実際の大規模PRより検出しやすい。
- off-by-one正例の初回実行は90秒でタイムアウトし、2回目の結果を使用した。
- LLMの反復実行による分散や信頼区間はまだ測定していない。
